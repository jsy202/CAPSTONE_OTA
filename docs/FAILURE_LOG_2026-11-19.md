## 실제 Pi3 감지로 교체 (`--verdict real`)

강제 판정 대신 보드 3대가 실제로 움직인다: Pi1이 CAN 0x200 주행 프로파일(정차 포함)을 보내고, Pi2에서 Qt 클러스터(코어 0 고정)와 IVI V2가 돌고,
Pi3 감시기가 baseline으로 지연을 보다가, V3 시험 중 지도 플래그가 켜지면 RT 부하가 걸려 Pi2 probation이 Pi3 판정을 읽는다.
정차 구간에서 판정이 실패면 롤백이 아니라 복구 거부 → 사고 흐름으로 이어진다.

| 관찰한 문제 | 확인한 원인 | 조치 및 확인 | 상태 |
|---|---|---|---|
| 실행이 `ssh` 종료 코드 255로 즉시 죽음 | `pkill -f <패턴>`을 원격 셸 한 줄에 넣으면 그 셸 자신의 명령줄이 패턴과 일치해 스스로를 죽임 | 정리 호출을 별도 ssh 호출로 분리 | 수정 |

### 범위 (과장하지 않기 위해)

- 롤백 거부의 원인은 **변조된 복구 슬롯**이다. CPU 경합 감지는 롤백이 일어나게 했을 뿐이고, 변조된 슬롯이 있으면 어떤 롤백이든 같은 거부가 나온다.
- 공격은 하되 지도를 열지 않아 V3가 통과하는 대조 실행은 **하지 않았다.** 커밋된 V3를 새 릴리스 버전 없이 되돌릴 수 없기 때문이다.
- 기기의 취약 모드(`recovery_verification=False`, 이벤트 `VULNERABLE_MODE_RECOVERY_UNVERIFIED`)로 V1 라디오 화면이 실제로 뜨는 "방어 실패" 시연은 **아직 하지 않았다.**
- 위 실행은 각 1회이며 통계가 아니다.
- 클릭과 승인은 사람이 아니라 내(보조 도구)가 수행했다. 사람이 승인을 누른 실행은 앞 절의 `field-real-screen`, `field-real-ui` 두 번뿐이다.
- 사고 보고의 `cluster: "unaffected"`와 `type: recovery_slot_tamper`는 코드의 상수이며 측정값이 아니다. 실제로 Pi3는 지도 부하 동안 클러스터 에코 지연이 약 1~3 ms에서 약 900~1800 ms로 오르는 것을 측정했다.

### 갱신 주기 올리기 (10 Hz → 50 Hz, 2026-11-20)

| 새 기준선으로도 `drift`가 가끔 뜸, 지연이 1 ms와 약 26 ms의 두 값으로 갈림 | 클러스터 화면 그리기(Canvas, JS)가 CAN을 받아 에코를 보내는 같은 스레드를 약 25 ms 막음 | 움직이는 층을 `Canvas.Threaded`로 바꿈. 지연 p99 약 26 → 약 16 ms, 50 Hz에서 64초 동안 `observing normal` 유지 | 부분 수정 |

- 설정 `profile_hz`(기본 10)가 주행 프로파일 주기와 감시기 기준선을 함께 정한다.

### 50 Hz 실제 감지 확인과 새 IVI 기준선 (2026-11-20)

- 지도 데이터가 빠진 3.1.0/3.2.0 대신 `--map`을 넣어 **V2 3.3.0 (svn 5) / V3 3.4.0 (svn 6)** 을 다시 만들고 일반 OTA로 Pi2에 설치했다(`ivi_rebaseline`). V3 릴리스에 `map.json`이 들어 있음을 `tar tzf`로 확인했다. 장치 슬롯 검사 통과.
- `bench.incident_field run --verdict real --decision approve`를 `profile_hz=50`으로 1회 실행했다(`.demo/hz50-verify`, `forced_verdict: false`).
  - 지도를 열기 전: 감시기 `observing / normal`, 최근 지연 약 17 ms.

## 2026-11-20 (밤) CPU 부하 크기 조사: 신호는 끊기지 않으면서 적당히 늦게 만들기

**배경:** 영상에서 지도를 열면 지연이 약 2980 ms가 되고 패널에 "모니터 신호 없음"이 떴다. 사용자가 "CPU를 거의 100% 스트레스 주는 것 아니냐, 신호가 안 끊기면서 적절한 지연이 나오는 점유율을 조사하라"고 했다.

**원인 확인(코드):** V3의 `ivi.json`은 `map_workers: "cores"`(코어 수만큼, Pi2는 4개), `map_priority: "rr10"`(실시간 SCHED_RR 10)이다. 워커 4개가 100% 바쁜 루프를 돌아 코어 0에 고정된 클러스터까지 굶긴다. "모니터 신호 없음"은 Pi3가 죽은 게 아니라, Pi2의 화면 피더가 ssh로 Pi3 판정을 읽다가(8초 제한) 굶어서 실패해 `lost`가 되는 표시였다.

## 2026-11-20 (밤 8) `검증 중`의 의미를 바로잡음

사용자 설명: V3로 갈 때의 별도 검증은 **CPU 검증이 아니라 V3가 정품이고 맞는 이미지인지만 보는 것**이다. CPU(지연) 검증은 업데이트 후 동작 중에 지연이 생기는 것을 보고 그때 롤백하는 것이다.

| 내가 잘못 잡은 것 | 바로잡은 것 |
|---|---|
| `검증 중` 팝업과 `업데이트 완료`를 "지연 감시가 통과할 때까지"의 구간으로 그렸다 | `검증 중` = 새 이미지로 바뀌는 순간(서비스 재시작과 이미지 점검, 장치의 `trial` 단계). 클러스터와 IVI 칸이 실제로 꺼졌다 켜지는 구간과 같다 |
| `업데이트 완료`를 지연 감시 통과 뒤(커밋)로 미뤘다 | `업데이트 완료` = 점검을 통과해 새 이미지가 돌기 시작할 때(`verify` 단계 시작). 그 뒤의 지연 감시는 동작 중인 업데이트의 감독일 뿐 검증 단계가 아니다. 지연이 생기면 `롤백 준비`로 이어진다 |

- 알림 순서: `업데이트 시작` → `설치 완료`와 `검증 중`(`trial` 단계, 두 칸 가림) → `업데이트 완료`(`verify` 단계) → (지연이 생기면) `롤백 준비` → … 이벤트 이름도 `accepted`에서 `updated`로 바꿨다.
- `trial` 단계가 기록에서 빠져도 `verify`만 보이면 순서대로 모두 알린다(시험으로 고정).
- 변하지 않은 것: 검증 구간 120초(`TRIAL_SECONDS`)는 "동작 중 지연 감시를 이만큼 지켜본 뒤에야 통과로 본다"는 감독 시간이다. 이름만 검증이지 CPU 검증이라는 뜻이다.

- **수정**: 장치에 `recheck_command`(ClusterDevice/ivi-update `--recheck-command`)를 추가했다. 게이트(`ota_gate`)는 update 항목에 `recheck_command`를 고정하고, 중계(`relay`)와 오케스트레이터(`gate_config`/`target_for`)가 같은 문자열을 만든다(다르면 거부, 시험으로 고정).

- **업데이트 시작 표시**: 장치는 `metadata`를 쓸 때 목표 버전을 모르고(`signature_verified`에서 안다) 알림이 그 시점의 화면 상태에 따라 `V2` 또는 `V2 -> V3`로 나왔다. 목표 버전을 안 뒤에 알림을 만든다.

## 2026-11-21 (밤) 내가 만든 회귀와 내가 잘못 읽은 표

- **회귀(내가 만듦)**: 롤백 후 확인을 따로 받게(`--recheck-command`) 고친 뒤, 사람이 승인한 복구가 `restore failed: actor exited unsuccessfully`로 실패했다. 복구 명령(`IncidentResponder._repair_command`)은 업데이트 명령에서 만들어지는데 새 인자가 그대로 남아 보안 게이트가 거부했다. 최종 상태가 `recovery_failed`로 끝난 방어 성공 실행에서 발견했다. 복구 명령에서 `--recheck-command`를 빼고, 게이트 시험을 추가했다(이전 시험은 recheck 없는 목표만 시험해서 못 잡았다). 교훈: 같은 설정을 여러 명령이 파생해 쓸 때는 파생 명령마다 시험한다.
- **잘못 읽은 표**: 영상을 3초 간격 그림표로 읽으면서, 시각 표시가 각 칸의 위쪽에 있어 게이지/속도를 한 줄씩 밀려 읽었고 "알림이 게이지보다 7초 빠르다"고 판단했다. 장치 단계 시각, 콕핏 데이터 지연(0.1~0.3초), 화면 갱신 수(초당 10~50번)를 차례로 측정한 뒤에도 안 맞아서, 영상 안에 실제 시계를 띄워 보니 알림과 게이지가 정확히 같은 순간이었다. 읽는 방법이 틀렸던 것이다. 이후로는 칸마다 시각을 붙여 한 줄에 (알림, 속도, 게이지)를 함께 그린 표로 확인한다.
- **수정/결과**: 방어 성공/실패 영상 모두 다운로드 완료 -> 감속 -> 0 -> 설치(차가 선 뒤 2~3초) -> 설치 100%와 `설치 완료`가 같은 순간 -> 부팅 0 -> 약 6초 뒤 가속. 롤백 후 `롤백 완료`는 확인 게이지가 찬 직후에 뜬다(방어 실패 영상 239초 -> 143초).

## 2026-11-23 Pi2에는 마우스가 없어서 지도 타일을 누를 수 없었다

- **문제**: 보드 시연을 직접 하는 중 V3의 지도가 켜지지 않았다. `--map-trigger ui`는 사람이 Pi2 화면의 지도 타일을 누르기를 기다리는데, Pi2에는 마우스도 터치도 없었다(입력 장치 목록에 HDMI뿐). 시작 전에 확인하지 않은 내 실수다. 가상 화면(Xvfb)일 때는 `xclick`(XTEST)으로 눌렀지만 HDMI 모니터에서는 그 방법이 통하지 않는다.
- **잘못된 첫 응급처치**: 눌린 효과만 내려고 표시 파일(`map_active`)을 직접 만들었다. 그러자 CPU 부하(지연)는 시작됐지만 **화면의 지도는 바뀌지 않았다.** 화면의 지도 페이지는 타일 누름으로만 바뀌고(`Ivi.qml`의 `page`), 파일은 부하 워커만 켜기 때문이다. 영상으로 쓸 수 없는 실행이 됐다.
- **수정**: Pi2에 리눅스 가상 포인터(uinput)를 잠깐 만들어 같은 위치(1050, 1387)를 실제로 누르게 했다(`bench/uinput_click.py`, `--map-trigger pointer`). 끝나면 장치를 지운다. 누르면 화면이 `page = "map"`으로 바뀌고 앱이 파일에 `1`을 쓰는 것을 확인했다. 시험 3개 추가.
- **한계**: 클릭이 정말 지도 페이지를 여는 것은 보드에서 한 번 눈으로 확인했지만, 이 새 경로(`pointer`)를 처음부터 끝까지 다시 돌려 보지는 않았다. 처음 클릭은 시연 도중 수동으로 했다.
- **중단 사고**: 시연이 도는 중에 내가 프로그램을 끊었더니 Pi2가 V3 시험 중인 채로 남았다. 그대로 두면 V3가 통과해 **확정**될 수 있어(되돌릴 수 없음) 시험 감시 프로세스를 멈춰 롤백시켰다. 두 번째 중단 뒤에는 공격 이미지가 슬롯을 바꿔 놓아 `recovery_failed`가 됐고, `ivi-repair`로 V2를 복원했다. 시연 중간에 프로그램을 끊으면 안 된다.
