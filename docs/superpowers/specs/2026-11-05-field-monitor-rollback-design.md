# 현장 감시 기반 호환성 검증과 지연 롤백 설계 (CPU 경합 단일 시나리오)

> **갱신 안내(2026-11-05)**: 이 문서는 초안이며 구현과 달라진 부분이 있다(수습 기간은 기존 trial 단계로, IVI V2는 지도 없음/V3가 지도 추가,
> 한 모니터 콕핏, 안전 창 판단 변경, 계약·정적 게이트는 미구현). 최종 내용은 `docs/IVI_FIELD_MONITOR_RESULTS_2026-11-05.md`와
> `docs/FAILURE_LOG_2026-11-05.md`를 본다.


프로젝트명은 변경하지 않는다: 「다중 ECU 환경에서의 OTA 소프트웨어 호환성 검증 및 자동 롤백 시스템」.
상태: 초안. 시나리오는 **IVI 업데이트로 인한 CPU 경합 하나뿐**이다. 아직 구현된 것은 없고,
미결정 사항은 마지막 절에 있다.

## 목표
업데이트 직후 시험으로는 드러나지 않는 **타이밍·자원 호환성 결함**을, 수습 기간 동안 독립 관찰자(Pi3)가
버스에서 상시 감시하다가 이상이 확정되면 **차량이 안전할 때** 이전 버전으로 되돌린다.

호환성 정의: 업데이트된 소프트웨어가 기존 ECU 기능의 **타이밍·자원 예산과 양립하는가**.
통합 컨트롤러(도메인/존) 환경에서는 한 기능의 업데이트가 같은 컴퓨트를 쓰는 다른 기능의 타이밍을
깨뜨릴 수 있고, 이것이 이 프로젝트가 다루는 비호환이다.

## 보드 역할
| 보드 | 역할 |
|---|---|
| Pi1 Central | 표준 주행 사이클 기반 차량 신호를 CAN 0x200으로 송신. OTA 파일 검증·중계. 업데이트 대상 아님 |
| Pi2 Cockpit | 계기판(기존) + IVI 앱(신규)을 별도 서비스로 실행. 계기판은 상태 에코 프레임을 CAN으로 송신. IVI의 A/B 업데이트·롤백 실행 |
| Pi3 Verifier | 버스를 수신 전용(listen-only가 가능하면 사용)으로 관찰하고 감지·확정·롤백 요청 |

IVI와 계기판은 한 보드 위의 논리적 ECU다. 물리적으로 별개인 ECU가 아니며, 통합 컨트롤러 환경을 모사한다는
점을 발표에서 먼저 밝힌다. 다중 ECU성은 (1) Central·콕핏·검증기가 같은 CAN 버스로 연결되고, (2) 업데이트 영향이
버스 위의 두 ECU 프레임 관계로 관측된다는 점에서 확보한다.

## 시나리오: IVI V3 CPU 경합
- IVI V3는 지도 타일 미리 불러오기(스레드 풀 크기 = 코어 수)와 60fps 애니메이션을 추가한다. 결함 코드는 없고
  정상 기능이다. 개발 PC에서는 부담이 작지만 Pi4 소프트웨어 렌더링 환경에서는 계기판과 코어를 두고 경합한다.
- 계기판 반응이 늦어지고(지연) 몇 프레임을 건너뛴다(끊김). 입력(CAN 0x200)은 끝까지 정상이다.
- 에코 기준 지연은 값이 일정한 구간에서도 측정된다. 렌더링 부하는 값이 변하는 구간(가속, 변속, 감속)에서 더 커질
  수 있으나 이는 Gate 0에서 측정해야 알 수 있는 가설이다.
- IVI를 정지 화면으로 두면 설치 직후 시험을 통과한다. 지도를 움직이는 동안에만 나타난다.
- 롤백 대상은 IVI (V3 → V2). 업데이트 전후 인과는 롤백 후 지연이 기준선으로 돌아오는지로 확인한다.

## 에코 프레임과 지연 측정
- 계기판이 CAN ID 0x300(충돌 여부 확인 필요)으로 상태 프레임을 송신한다: 표시 속도, 반영한 원본 카운터, 유효
  플래그, 서비스 시작 번호.
- Pi3는 같은 시계(커널 수신 타임스탬프 `SO_TIMESTAMPNS`)로 0x200과 0x300을 받아 **카운터가 같은 쌍**을
  매칭해 지연을 계산한다. SSH 경유 지연과 보드 간 시계 오차가 없다.
- 한계: 타임스탬프는 MCP2515/SPI 인터럽트 경로를 거친 커널 수신 시각이라 서브밀리초 오차를 포함한다.
  보고서에 측정 불확실도를 적는다.
- 보안 참고: 계기판 서비스가 CAN 송신 권한을 갖게 된다. 임의 프레임 송신 가능성은 범위 밖의 한계로 기록한다.

## 계약 (contract.json)
릴리스에 포함되고 `release.json`의 `contract_sha256`으로 서명 체인에 묶인다.
- `resource_budget`: 릴리스가 선언하는 자원 예산(예: CPU 점유 상한). 개발 환경에서 측정한 값이므로 타깃 보드의
  실제와 다를 수 있다. 정적 게이트는 선언이 차량 기준 정책 안인지만 본다.
- `probation`: 수습 기간(주행 시간 또는 사이클 수)
- `safe_window`: 정차 지속 시간 등
- `monitors`: 감시 규칙 (지연 상한, 끊김 길이, 갱신 누락 비율)

Pi3의 차량 기준 정책이 하한이다. 릴리스 규칙은 **강화·추가만 가능**하고 완화(예: 안전 창 단축, 지연 상한
증가)는 계약 전체를 거부한다. Pi3는 자기 공개키로 서명을 직접 검증한다. 선언된 예산과 실측의 차이는 정적
선언의 한계를 보여 주는 증거로 쓴다.

## 감지
정답 없이 판단하는 방식과 정답이 있는 방식을 겹친다.
1. 계약 규칙: 지연 상한, 끊김 길이.
2. 지연 꼬리: 변화 구간의 p99 지연을 기준선과 비교.
3. 변화점 검출: 지연과 갱신 간격에 EWMA/CUSUM.
4. 드리프트: 지연 추세 기울기 검정.
5. 고장 서명 분류: 지연형(전반적으로 늦음), 끊김형(갱신 정지 후 점프), 입력 이상형(Central 프레임 자체의
   주기 이상, 업데이트 탓이 아님)을 구분한다.

확정은 점수 누적 + 지속 시간 + 독립 기법 2개 이상 합의로 한다. 임계값은 정상 운전 보정 데이터의 분위수로
정하고, 보정과 평가는 서로 다른 주행 사이클로 분리한다. ML은 쓰지 않는다. 업데이트 탓인지는 업데이트 전
기준선과의 비교와 롤백 후 재검증으로 판단한다.

## 수습 기간 상태 기계
`관찰 → 의심(Suspect) → 확정(Confirmed) → 롤백대기 → 안전 창 → 롤백 → 재검증`, 이상이 없으면 수습 종료 후
정식 확정.
- 롤백 요청은 Pi3가 하고 Pi2 업데이터가 **자기 쪽에서 안전 조건을 다시 확인**한 뒤 실행한다.
- 안전 창: 버스 기준 속도 0이 N초 지속. 릴리스가 완화할 수 없다.
- Pi3 하트비트가 끊기면 "감시 불가"로 표시하고 수습을 종료하지 않는다 (fail-closed).
- 의심 시점 직전 N초의 CAN 프레임, 에코, 점수를 프리즈 프레임으로 저장한다.

## 데이터셋
- 입력: 표준 주행 사이클의 속도 (EPA UDDS/HWFET, WLTC)를 10Hz로 보간하고 기어와 rpm을 파생한 합성 신호.
  가속도 제한, 기어-rpm 상관 같은 물리적 타당성을 시험으로 고정한다. 정차 구간은 안전 창 시험에 쓴다.
- 녹화: Pi3 `candump` 트레이스를 골든 트레이스로 보관한다. 조건: V2 정상 반복, V3 부하 단계(0/25/50/75/100%),
  사이클 3종.
- 사이클 파일의 출처와 이용 조건은 받아서 확인한 뒤 저장소 포함 여부를 정한다.

## 지표와 증거
- 지연(p50/p99), 최대 끊김 길이, 갱신 누락 수, 감지 지연, 정상 장시간 오탐률, 임계값 스윕, 분류 혼동 행렬.
  측정된 값만 보고한다.
- 요구사항 ID → 규칙 ID → 시험 ID → 증거 (JUnit, Allure, CAN 로그, 프리즈 프레임).
- 시험 수준: 단위(합성·골든 트레이스 재생), 하드웨어(기존 `--hardware-config` 옵트인).

## 주장하지 않는 것
- 특정 제조사의 실제 사고 재현, 실제 장기 사용 결함 재현, 실차 데이터 일반화.
- 물리적으로 별개인 ECU 간의 신호 의미 비호환(이번 범위 밖).
- 광학적 화면 검증 (Pi3는 모델·QML 수준 값과 CAN 에코를 본다).
- CAN 위조 프레임 같은 침입 탐지.
- 시연의 시간 압축·가속은 가속이라고 명시한다. 부하 크기와 지연 상한 기준은 설계자가 정한 값이다.

## 위험과 미결정 사항
1. **Gate 0**: Pi2에서 IVI 부하 시 계기판 지연이 실제로 늘어나는가. 이 시나리오가 유일하므로, 성립하지
   않으면 부하 기능의 크기 조정(정상 기능 범위 안에서) 또는 시나리오 재논의가 필요하다.
2. Pi3 `listen-only`에는 root가 필요하다 (sudo 비밀번호 미상). 대안: 부팅 시 설정, 또는 일반 수신 + 한계 명시.
3. 0x300 ID 충돌, Pi2 CPU/RAM/스왑, 커널 PSI 지원 여부 확인 필요.
4. Pi3 재부팅과 저전압 이력, Pi2 부하 시 발열·전원. 시험 중 `vcgencmd get_throttled`를 함께 기록하고
   부하는 짧게 끊어서 건다.
5. 한 보드 위 두 앱이라는 점이 "다중 ECU" 주장의 약점이다. 위 보드 역할 절의 설명 틀로 방어하고 한계를 먼저
   말한다.
