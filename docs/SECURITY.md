# 보안 모델과 제한

## 보호 자산과 신뢰 경계

- 노트북의 `update-signing.key`는 릴리스 승인 권한입니다. 오프라인 백업하고 Pi나
  저장소에 복사하지 않습니다.
- 개발 CA 개인키는 모든 MQTT/HTTPS 신원을 만들 수 있으므로 서명키와 동일하게
  보호합니다.
- Pi에는 로컬 CA, 장치 전용 MQTT 인증서/개인키, Ed25519 공개키만 둡니다.
- 동일 LAN도 완전히 신뢰하지 않습니다. 네트워크 경계에서는 TLS, 업데이트
  경계에서는 별도의 Ed25519 서명을 검증합니다.

## 방어하는 공격

- MQTT 도청·변조 및 다른 장치 토픽 접근: mTLS와 인증서 CN 기반 ACL
- 가짜 HTTPS 서버: 로컬 CA와 hostname/IP SAN 검증
- 릴리스 변조: 서명된 manifest, artifact 크기와 SHA-256
- 재전송·다운그레이드: 완료 job 영속화, 만료시간, 현재보다 큰 SemVer 요구
- tar 경로 탈출: 절대/상위 경로, 링크, 특수 파일 거부와 개수/크기 제한
- 불완전 활성화: staging과 같은 파일시스템에서 원자적 이동/링크 교체
- 새 앱 부팅 실패: 제한시간 systemd 헬스체크와 이전 링크 자동 복구

## 운영 권한

`digital-dash` 계정은 릴리스 디렉터리를 쓰지 못합니다. `capstone-ota` 계정만
staging/releases를 수정하며 polkit은 `digital-dash.service` 관리만 허용합니다.
Mosquitto publisher는 모든 장치 명령 쓰기/상태 읽기, 각 Pi는 자기 ID 토픽만
읽기/쓰기가 가능합니다.

## 키 회전과 폐기 제한

현재 schema는 하나의 업데이트 공개키와 개발 CA를 사용하며 복수 키, 임계 서명,
자동 폐기 목록이나 무중단 키 교체 프로토콜이 없습니다. 키 유출 시 LAN 차단,
broker/HTTPS 중지, 새 CA·장치 인증서·업데이트 키의 수동 재프로비저닝이 필요합니다.
서명키 교체 릴리스를 기존 키 하나만으로 신뢰시키는 방식은 키 탈취 상황을 해결하지
못합니다.

## 양산 적용 전 필요한 것

이 구현은 Uptane/TUF 완전 구현이 아닙니다. 실제 차량에는 최소한 다음이 더
필요합니다.

- 오프라인 root와 역할별/임계 서명, HSM 또는 보안 요소
- 키 폐기·회전, ECU별 inventory와 배포 승인 정책
- primary/secondary ECU 프로토콜과 전체 차량 호환성 검사
- 전원 차단·저장장치 오류에 대한 부트 체인/A-B 파티션 검증
- 코드 서명된 OS/부트로더, secure boot, 원격 attestation
- 중앙 감사 로그, 배포 취소, staged rollout과 안전 사례 검증
- 자동차 사이버보안 및 소프트웨어 업데이트 관련 적용 규정 검토
