# OS 파티션 A/B OTA — 설계 스케치 (미착수, 보류 단계)

이 문서는 지난 대화에서 "지금은 앱 디렉터리 A/B만 하고, OS 파티션 A/B는 나중에"로 보류한
작업을 위한 **설계 초안**입니다. 코드는 없고, 다음에 손댈 때 바로 시작할 수 있게 뼈대만
남겨 둡니다. **보드는 전혀 건드리지 않았습니다.**

## 왜 아직 안 했는가

1. 이번 세션의 핵심 작업(디버그 포트 롤백 방어)과 직접 관련이 없습니다. 방어 메커니즘
   (`Device._verify_record`의 커밋 시점 해시 고정 재검증)은 교체 단위가 "앱 폴더"든
   "OS 이미지 전체"든 똑같이 적용되므로, 이걸 먼저 끝내는 게 맞다고 판단했습니다.
2. OS 파티션 전환은 부트로더(U-Boot) 설정을 바꾸는 작업이라, 실패하면 보드가 안 부팅될
   위험이 있습니다. 사용자 부재 중에 라이브 보드에서 시도하는 건 범위를 넘는다고 판단했습니다.

`rauc` CLI는 사용자가 비밀번호를 제공해 설치했고(`apt-get install rauc`), **로컬 PC에서만**
포맷 검증용 테스트 번들도 만들어 서명·검증까지 확인했습니다 — `deploy/os-ab/local-format-test.raucb`가
그 결과물입니다 (자체 서명한 테스트용 CA/인증서로 만든 더미 페이로드, 실제 롤아웃과 무관).
보드는 여전히 전혀 건드리지 않았습니다.

```
$ rauc --cert=dev.cert.pem --key=dev.key.pem bundle content/ local-format-test.raucb
$ rauc --keyring=local-test-ca.cert.pem info local-format-test.raucb
Compatible:   'capstone-cockpit'
Version:      '0.0.1-localtest'
Verifying bundle signature...
Verified detached signature by 'O = capstone-ota-test, CN = test-only-dev'
```

이걸로 "RAUC 번들 생성·서명·검증 포맷이 이 환경에서 실제로 동작한다"는 건 확인됐습니다.
남은 건 실제 보드 파티션 구조와 U-Boot 통합뿐입니다.

## 추천 도구: RAUC (Yocto 아님)

이유는 이전 대화에서 설명한 대로입니다 — 기존 Raspberry Pi OS(Debian)를 그대로 쓰고,
루트 파티션만 두 번째로 추가하면 되기 때문에, 처음부터 배포판을 새로 빌드하는 Yocto보다
훨씬 적은 작업으로 끝납니다.

## 구조

```
[1단계: 뼈대 세팅 — 보드마다 한 번만, 물리적 접근 필요할 수 있음]
  - SD카드에 루트 파티션 두 개(A/B) 만들기
  - U-Boot에 "부팅 슬롯 선택 + 부팅 실패 카운트 + 자동 폴백" 스크립트 설치
  - rauc 설치, system.conf로 두 슬롯 등록

[2단계: 실제 OTA — 그 뒤로는 완전히 무선, 지금 앱 폴더 A/B와 같은 흐름]
  - 서명된 .raucb 번들을 네트워크로 전송
  - 비활성 루트 파티션에 설치
  - 재부팅 → 새 파티션 시도 → 성공/실패 카운트
  - 실패 시 U-Boot가 자동으로 이전 파티션으로 복귀
```

## 이번 세션에서 만든 방어와의 관계

디버그 포트 공격·복구 직전 재검증 방어는 **그대로 재사용됩니다.** `Device._verify_record`가
지금은 "앱 폴더의 트리 해시"를 커밋 시점에 고정해 두고 복구 직전에 재검증하는데, OS
파티션 버전에서는 "비활성 루트 파티션 전체의 해시(또는 RAUC가 이미 관리하는 slot status
파일의 체크섬)"를 똑같은 방식으로 고정·재검증하면 됩니다. **디버그 포트로 비활성 파티션의
내용을 바꿔도, 부팅 직전에 그 해시가 커밋 때 기록한 값과 다르면 부팅을 거부**하는 식으로
그대로 확장됩니다.

## 다음에 할 일 (순서)

1. 보드 하나(Pi2 추천 — 이미 가장 많이 만져 봄)에서 SD카드를 **복제해 둔 뒤** 파티션
   구조 변경 시도. 복제본이 있어야 실패해도 바로 되돌릴 수 있음.
2. `deploy/os-ab/system.conf.template`을 실제 슬롯 장치 경로로 채우기 (복제한 SD카드
   기준으로 실제 파티션 번호 확인 후).
3. U-Boot 스크립트는 RAUC 공식 문서의 Raspberry Pi 예제를 거의 그대로 가져다 씀
   (이 프로젝트가 새로 설계할 부분이 아님)
4. `Device._verify_record`의 해시 고정·재검증 로직을 `capstone_ota`에 "OS 슬롯"
   버전으로 하나 더 만들거나, 기존 로직이 "슬롯 디렉터리"가 아니라 "슬롯 블록 디바이스"도
   받을 수 있게 확장

## 하지 않은 것 (명확히)

- 보드 SD카드 파티션 변경 (위험, 사용자 부재 중 시도 안 함)
- U-Boot 스크립트 작성/테스트
- `capstone_ota`의 OS 슬롯 확장 코드
- 실제 보드용 서명 키 생성 (`local-format-test.raucb`는 테스트용 자체 서명 키로, 실제
  배포에는 절대 쓰면 안 됨)
