# 시행착오와 검증 기록 — 2026-11-17 ~ 18 (게이트웨이 사고 대응)

범위: Pi1 진단 게이트웨이 경유 공격, 관제 서버 사람 승인, 서명된 일회용 복원 지시서, 그리고 그 뒤 보안 보강.
모든 구성요소는 한 노트북의 프로세스이며 실보드 검증은 하지 않았다.

| 관찰한 문제 | 확인한 원인 | 조치 및 확인 | 상태 |
|---|---|---|---|
| "Pi1이 릴리스를 이미 캐시하고 있다"고 설명함 | 사실 확인 없이 말함. `relay.forward`는 임시 디렉터리만 쓴다 | 사용자에게 정정하고, 복원 때 서버에서 받아 서명 검증하도록 설계(`cache_release`) | 설계 반영 |
| 첫 커밋이 `Author identity unknown`으로 실패 | 새로 clone한 저장소에 git 사용자 정보가 없었음 | 저장소 로컬로 이름·이메일 설정(전역은 건드리지 않음) | 해결 |
| 기준선 시험 `test_local_cockpit_replay`가 `ModuleNotFoundError: PIL` | 새 venv에 `cockpit` extra가 없었음(코드 문제 아님) | `pip install -e '.[dev,cockpit]'` 후 전체 313 passed | 환경 문제 |

| 독립 리뷰: 게이트를 닫은 뒤에도 이미 시작된 업로드가 끝까지 전달됨 | 닫힘 여부를 연결 시작 시점에만 확인 | 재현 시험(RED) 작성 후, 청크마다 `is_open` 재확인(GREEN) | 수정 |
| 독립 리뷰: 응답이 쓰레기일 때 응대기가 예외로 죽음 | `HTTPException`/`TypeError`를 안 잡았고 incident id 형식 검증이 없었음 | 예외 범위 확대와 `INC-\d{4,}` 검증, 시험 추가 | 수정 |
| 독립 리뷰: 서버를 재시작하면 사고 기록이 사라짐 | 메모리 목록만 있고 저장소를 읽지 않았음 | 시작 시 `_load()`로 검증·복원. 손상된 저장소는 덮어쓰지 않고 시작 거부 | 수정 |

| 해시 강조 UI 변경 뒤 시험 실패 | 해시가 강조 `span`으로 쪼개져 문자열 포함 비교가 깨짐 | 태그를 지운 보이는 텍스트로 비교 | 시험 수정 |

| 관찰한 문제 | 확인한 원인 | 조치 및 확인 | 상태 |

| 느린 연결이 게이트웨이를 붙잡을 수 있음 | 연결 수 제한이 없고 시간 제한이 읽기 1회당이었음 | `max_connections`(초과는 `ERROR gateway busy`), `request_deadline`. 시험 2개 | 수정 |

| 지시서 버전을 보고한 커밋 버전과 비교하지 않음 | 서버를 신뢰하는 쪽으로만 설계함 | `accept_order(..., version=)`. 다르면 거부하되 일회용 표시는 하지 않음(정상 지시서를 막지 않게). 시험 | 수정 |
| 승인 버튼이 항상 "V2로", 이미 처리된 사고에 빈 페이지 | 버전을 문구에 하드코딩, 409에 본문 없음 | 보고된 커밋 버전으로 표시, 읽을 수 있는 409 안내 페이지 | 수정 |
| 강제 종료 시 `.repair-*`·`.download-*` 임시 디렉터리가 남음 | `TemporaryDirectory`는 정상 종료만 정리 | `repair()` 시작 시 잠금 안에서 남은 디렉터리 삭제. 시험 | 수정 |

### 아직 남은 것

- 운영자 로그인과 DNS 리바인딩(Host 검사), 서버 쪽 연결 수 제한은 없다.
- `--api-token-file`은 공유 비밀이다. 차량별 인증이 아니다.
- 분산 공격이나 대역폭 소진은 막지 못한다.
- 전부 실보드에서 확인하지 않았다.
