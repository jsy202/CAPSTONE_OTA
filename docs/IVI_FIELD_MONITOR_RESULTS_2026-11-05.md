# IVI 업데이트(V2 → V3 지도 추가)가 클러스터를 느리게 만드는 문제: 수습 감시와 안전한 롤백 (2026-11-05)

증거: `.demo/ivi-e2e-final2-20261105/`(최종 실행, 모니터 화면 캡처 5장 포함), `.demo/gate0-20261105/`.
실패와 해결의 전체 기록은 `FAILURE_LOG_2026-11-05.md`. 모든 수치는 1회 실행의 측정값이다.

## 시나리오
- **IVI V2**: 지도가 없는 헤드유닛. **IVI V3**: 내비게이션 지도(서울 시청 주변, OpenStreetMap 도로 데이터)가 추가된 버전.
- V3에서 지도를 열면 **배경 타일 선읽기 워커**(코어 수만큼, 실시간 SCHED_RR 우선순위 10)가 동작해 같은 보드의 디지털
  클러스터 처리가 늦어진다. 이 워커가 부하의 정체이며, 지도 화면 자체의 렌더링 부하가 원인이라고 주장하지 않는다.
- Pi3(독립 관찰자)가 버스에서 지연을 판정하고, 확정되면 **차량이 정차했을 때** V2로 롤백한다.

## 구성 (한 모니터, Pi2 HDMI 2160×1440)
왼쪽 위 실제 Qt 클러스터(실시간 캡처, 버전 글자 없음) · 오른쪽 위 업데이트/Pi3 판정/지연 기준/CAN 값 대 클러스터 표시값 ·
가운데 현재 슬롯의 IVI(버전 배지, 색 구분) · 아래 이벤트 로그. 지연 요구사항: **창 p99 처리 지연 ≤ 100ms(CAN 1주기)**.
클러스터 지연은 클러스터가 프레임을 처리한 직후 보내는 CAN 0x300 에코와 원본 0x200의 같은 시계 차이로 잰다.

## 최종 실행 결과 (`.demo/ivi-e2e-final2-20261105/`)
| 단계 | 지연 p50 | p99 | 최대 | 최대 끊김 | 누락 |
|---|---|---|---|---|---|
| V3 설치 직후, 지도 닫힘 | 1.3 ms | 9.8 ms | 14.8 ms | 113 ms | 0 |
| **V3, 지도 열림** | **608 ms** | **1854 ms** | **1996 ms** | **2012 ms** | **15 %** |
| 롤백 후 V2 | 2.1 ms | 17.2 ms | 59.3 ms | 154 ms | 0 |

- 지도를 연 뒤 6초에 의심, 16초에 확정(기준 위반 + 지연·끊김 규칙 동시 발화). 의심까지는 요구사항 위반 하나로도,
  확정은 3개 창 지속으로 판정한다.
- 롤백은 **속도 0km/h, 차량이 12.1초 정차 중**일 때 시작(`rolled back in safe window`, 300초 폴백 아님). 롤백한 V2는
  62초 재검증을 통과했고 최종 상태는 `rolled_back`, 버전 2.0.0이다.
- 안전 창은 Pi2 자신의 버스 관측과 Pi3의 버스 관측이 모두 정차를 말할 때만 열린다(Pi3가 응답하지 않으면 Pi2 단독,
  결과에 그렇게 표시).

## 구현
- 계기판: 처리 직후 CAN 0x300 상태 에코(`main.cpp`), 버전 배지 비표시.
- `capstone_ota/monitor/`: 트레이스 파서, 창 지표, 감지 규칙 7개(선언 기준 `latency_limit` 포함), 확정 로직, Pi3 실시간
  감시기(리셋 nonce, 프리즈 프레임), Pi2 빠른 버스 탭.
- `capstone_ota/probation.py`: 수습 감독기(안전 창 판단 기록, 관측 유예, 리셋 nonce), `capstone_ota/ivi.py`와 CLI
  `ivi-update`: IVI 슬롯 A/B 관리(기존 검증된 복구 경로 재사용).
- `dashboard/ivi/`: 목업 IVI(V2 지도 없음, V3 지도+워커, 화면 QML 포함), `dashboard/cockpit/`: 한 모니터 화면.
- `bench/`: 주행 프로파일, 재생기, 시뮬레이터, 부하 생성기, 단계별 분석, 지도 데이터·릴리스 생성, 콕핏 피더.

## Gate 0 (참고): 어떤 CPU 부하가 계기판을 늦추는가
같은 우선순위의 CPU 점유 프로세스(최대 8개), `nice -10`, 실시간 2개는 영향이 없었고(p99 ≤ 5.1ms), **실시간 4개(전 코어)** 에서만
p99 1127ms였다. 그래서 V3의 워커를 이 조건으로 구성했다.

## 한계 (주장하지 않는 것)
- **V3 워커가 실시간 우선순위로 전 코어를 점유하는 것은 설계한 부하다.** 실제 IVI 지도 앱의 동작이나 특정 사고의 재현이
  아니다. 실제 시스템에서는 cgroup CPU 격리·RT 제한으로 막는다. 지연 크기(약 1~2초)는 이 구성의 결과이고 워커 수로 조절된다.
- "지도 열기"는 시연 스크립트가 플래그 파일로 대신했다. 지도는 타일이 아니라 OSRM 경로와 Overpass 도로 데이터를 직접 그린 것이다
  (OSM 타일 서버는 대량 내려받기로 차단되어 사용하지 않음, 우회하지 않음).
- 지연은 처리 직후 에코 기준이며 화면 픽셀 기준이 아니다. 수치는 1회 실행이고 반복 측정은 하지 않았다.
- 롤백은 확정 후 다음 정차까지 대기하므로, 그동안(이번 실행에서는 지도를 연 시점부터 롤백까지 약 100초) 클러스터가
  늦은 채로 주행한다. 즉시 전환(failover)은 구현하지 않았다. 정차 중 롤백의 여유는 약 2초로 작다(`--safe` 조정 여지).
- **계측기가 시스템에 영향을 줄 수 있어** 클러스터를 코어 0에 고정하고 계측기를 코어 1~3에 두었다(경합 시나리오는 유지).
  그 결과가 고정 없는 구성과 같다는 보장은 없다.
- 마지막 수정(에코 대기 프레임을 지연에 반영, 글자 잘림 수정) 이후의 라이브 화면 확인은 하지 못했다(단위 시험으로만 검증).
- 보드 한계: Pi3 저전압 이력(`0x50000`), Pi2 열 제한 이력(`0xe0000`), Pi3 감시기는 재부팅 시 자동 시작하지 않음.
- 주행 데이터는 합성 사이클이다. 구현하지 않은 것: 서명된 릴리스 계약과 tighten-only 병합, 설치 전 정적 호환성 게이트,
  Pi3 listen-only(sudo 없음), 프리즈 프레임의 자동 시험 편입.
