# 가상 환경에서 첫 시나리오 실행하기

**기본 OTA는 그대로 두고, 재연결 결함 → 복구 → 복구 슬롯 바꿔치기 차단을 확인한다.**

저장소 루트에서 기존 가상 환경을 사용한다.

```bash
. .venv/bin/activate
python -m demo.run --output .demo/compatibility
```

이미 존재하는 출력 폴더에는 덮어쓰지 않는다. 다시 실행할 때는 `.demo/compatibility-2`처럼 새 이름을 쓴다.
개인키는 출력 폴더의 `keys/`에만 만들고, HTTP로 제공하는 `releases/`에는 넣지 않는다.

## 무엇을 보여주는가?

```text
V2 정상
 ↓ V3 시험 설치 — 서명·해시·초기화 모두 통과
입력 소스 재연결
 ↓ V3가 송신 객체를 다시 만들어 메시지 번호까지 초기화
Cluster가 순서가 맞지 않는 프레임을 거부
 ↓ 검증기가 입력과 실제 수신 모델의 갱신을 대조해 실패 판정
V2 복구
 ├─ 원래 V2가 있으면: V2 재검증 후 복구 성공
 └─ V1으로 바꿔치기됐다면: 기록된 V2의 해시와 달라 실행 전 차단
```

실행 결과는 세 줄로 출력하고 자세한 증거는 `.demo/compatibility/result.json`에 남긴다.

| 비교 | 실제 결과 |
|---|---|
| 기본 초기화 검사만 사용 | V3를 확정해버림. 재연결 결함을 검사하지 않음 |
| 외부 호환성 검증 추가 | V3 거부 → V2 복구·재검증 |
| V2 복구 슬롯을 정상 서명된 V1으로 교체 | `recovery_failed`: V1 초기화·실행 전에 복구 거부 |

공격 경우에는 V2가 없어졌으므로 정상 복구 성공이라고 말하지 않는다. V1 차단에서 시연을 끝낸다.
현재 선택자는 실패 후보 V3에 남을 수 있으며, 이 결과를 운행 가능·정상 서비스 상태로 해석하면 안 된다.

## 결함이 단순히 실패값을 반환하는 것은 아닌가?

V2와 V3는 같은 입력 처리·프레임 인코더를 사용한다. 다른 부분은 실제 송신 객체의 수명 관리다.

- `demo/publisher_v2.py`: 재연결해도 같은 Sender를 사용한다.
- `demo/publisher_v3.py`: 연결 초기화 함수를 재사용하면서 Sender까지 새로 생성한다.

검증기는 먼저 8개 입력을 보내 정상적인 `250,251,...,255,0,1` 순환을 확인한다.
그다음 재연결하고 새 입력 6개를 보낸다.

| 관측 | V2 | V3 |
|---|---|---|
| 초기화 | 통과 | 통과 |
| 프레임 형식·CRC·신호 범위 | 통과 | 통과 |
| 재연결 전 처리 | 8개 수락 | 8개 수락 |
| 재연결 후 번호 | 2~7 | 250~255 |
| 재연결 후 처리 | 6개 수락 | 0개 수락 |
| 수신 모델 속도 | 새 값 65.0 km/h | 이전 값 47.0 km/h에 머묾 |

계속 프레임을 보내지만 소비하는 쪽에서 처리가 끊긴다. 검증기는 Central의 성공 응답만 믿지 않고,
별도 Cluster 프로세스에서 실제 갱신된 모델 값을 자기 입력과 비교한다.

## 복잡도를 늘리지 않기 위한 경계

`capstone_ota/`의 기본 코드·메타데이터·CLI는 변경하지 않았다. `demo/run.py`의 작은 어댑터가
기존 Device의 초기화 검사 뒤에 외부 검증기를 호출한다. 현재 일반 `ota update` 명령에
독립 검증이 자동 적용된 것은 아니다. 다음 실물 통합 전 검증하는 가상 실험이다.

Central과 Cluster는 별도 프로세스, 검증기는 별도 프로세스다. **한 노트북에서 stdin/stdout으로
8바이트 CAN 페이로드를 전달하는 시뮬레이션**이며, 물리 CAN이나 커널 vcan은 아니다.
실시간 주기·버스 부하·CAN 중재·Qt 픽셀·세 Pi의 물리적 독립성은 확인하지 않는다.

여기서 Cluster는 순서가 틀린 프레임을 거부하는 고정 계약의 수신 모델이다. 모든 양산 ECU가
이 정책을 사용한다는 뜻이 아니다. 각 검증은 새 앱/수신 세션으로 시작하며, 그 세션 안의
소스 재연결이 수신 상태를 초기화하지 않는다는 조건을 검사한다. 실행 중인 실제 Cluster의
업데이트 전후 세션 재동기화까지 구현한 것은 아니다.

V1은 `1.0.0/SVN1`인 **서명된 구버전 정책 시험물**이다. 이 단계에서 V1의 실제 취약점이나
해킹 성공을 구현·입증한 것은 아니다. V2로 바로 시작하므로 V1 사용 이력도 필요 없다.
V3와 V2의 SVN은 모두 2여서, 이번 V3 실패는 보안 버전 검사 대신 실제 호환성 검사로 발생한다.

바꿔치기는 데모가 소유한 복구 슬롯에만 수행하는 통제된 공격 주입이다. 공격자가 실제 Pi에서
그 쓰기 권한을 얻는 취약점은 재현하지 않는다. V2의 보호된 기록·공개키·검증기를 바꾸지 않은
조건에서 V1의 정상 서명과 파일 해시까지 확인하고 삽입한다. 복구는 보호된 V2 기록의 트리 해시가
달라져 거부된다. 즉 **파일 서명 유효성과 이 거래의 복구 대상으로 허용됨은 다르다.**

## 파일 위치

- `demo/central_app.py`, `publisher_v2.py`, `publisher_v3.py`: 서명할 실제 후보 앱.
- `demo/cluster.py`, `verify.py`: 앱 바깥의 고정 수신 모델과 판정 로직.
- `demo/run.py`: 패키징·실제 HTTP/A-B·통제된 슬롯 교체를 묶는 가상 실험.
- `tests/test_virtual_compatibility.py`: 정상 순환, 재연결, 판정 실패·시간 제한과 전체 흐름의 회귀 시험.

실험 데이터·개인키는 Git에서 제외된 `.demo/`에 두며, 기존 Pi 서비스와 SD에는 손대지 않는다.
